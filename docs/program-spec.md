# Heirloom program spec (source of truth for contract, IDL and TS client)

Every agent builds against this file. If you must change it, change it here first and say so in your report.

- Program name: `heirloom` (Anchor 1.2.2, Rust). Program id: **`b3PBVwkLnyx7eyLPNtc5J3Ds3os3cenqCVRHaCJM7FY`**
  (keypair at `target/deploy/heirloom-keypair.json`, gitignored; keep that file to keep the id). The TS side reads
  `NEXT_PUBLIC_HEIRLOOM_PROGRAM_ID`. The IDL is `app/src/lib/chain/idl/heirloom.json` (generated by `anchor build`).
- Money: USD₮ SPL token, 6 decimals. All amounts are `u64` base units (1 USD₮ = 1_000_000).
- Times: `i64` unix seconds from `Clock`.
- Hashes: `[u8; 32]` SHA-256 of the off-chain file/JSON. No personal data on-chain, ever.
- Token transfers use `transfer_checked` (token program = classic SPL Token; Token-2022 not required).
- Bitmaps: verifier index i (0..3) sets bit `1 << i`. Count with `count_ones()`.

Signer roles: **owner** (estate.owner), **agent** (estate.agent), **verifier** (one of estate.verifiers), **beneficiary** (wallet with an active Beneficiary PDA), **buyer**, **anyone**.

**Living plans** (added 2026-11-11): a `starts_now` rule already works while the owner is alive (estate Active): claims need the agent + the **owner** (`owner_approve_claim`), verifiers alone are not enough; after unlock the verifier quorum (or an earlier owner approval) counts. Scheduled payments (`recurring_amount > 0`) are paid by anyone calling `execute_scheduled` once due. No minimum interval or waiting period: 60 s works for devnet demos.

Losing offers are returned by the buyer calling `withdraw_offer` (works in any asset state).

### Clarifications made while implementing (contract author, 2026-11-11)
- `submit_death_claim`: `cert_hash` must be non-zero (NoDeathClaim) and only one open claim at a time: fails with
  BadStatus if `death_cert_hash ≠ 0` (stops a second submission resetting attestations). A rejected or vetoed claim clears it.
- `review_death`: also requires status Active and `death_verdict == Pending` (BadStatus), so the agent can't re-review after DeathPending.
- `attest_death`: also requires a claim (NoDeathClaim); allowed in Active **or** DeathPending; only the attestation that
  reaches `death_threshold` starts the timer (later attestations don't reset `death_pending_since`).
- `create_estate` vault, `place_offer` escrow: `init_if_needed` (anyone can pre-create an ATA, which would otherwise block the call).
- `execute_claim`: also checks estate status (see row 18). `approve_hardship`: also requires asset not Sold (BadStatus).
- `list_asset` wrong signer → NotAgent; `duration_secs > 0` (InvalidAmount). `add_rule`: Beneficiary PDA must be active (NotBeneficiary); bad caps → InvalidAmount.
- `register_asset`: nft mint needs decimals 0 **and** supply 1 (InvalidNft); bad prices → InvalidAmount.
- `withdraw_offer` / `accept_offer` move the whole escrow balance (≥ offer.amount) so the escrow close can't fail.
- Mint checks: `usdt_mint` account `address = estate.usdt_mint` and every owner/buyer USD₮ token account `mint == estate.usdt_mint`, both → WrongMint.

## Off-chain hashing convention
`hash = sha256(bytes)`; for JSON use canonical JSON (keys sorted, no whitespace). Shown in UI as hex.

## Account names the TS client resolves (added by the backend agent, 2026-11-11)
`app/src/lib/chain/instructions.ts` resolves accounts **by name from the IDL** (case/underscore-insensitive), so any order works,
but names must be one of these. Preferred name first; aliases in brackets also work.
- Signers: `owner`, `agent`, `verifier`, `buyer`; beneficiary-signed ixs (submit_*): `beneficiary` = signing wallet + `beneficiary_account` = Beneficiary PDA (as in the IDL); `finalize_unlock` / `execute_claim`: `payer` [`signer`]; `list_asset`: `authority` [`signer`].
- PDAs: `estate`, `beneficiary` (the Beneficiary PDA in add_rule), `payee` (Payee PDA), `rule`, `claim`, `asset`, `offer`, `hardship`.
- Plain wallets (unchecked): `wallet` (add_beneficiary/add_payee), `payee_wallet`, `recipient` (accept_offer USD₮ receiver).
- Mints: `usdt_mint` [`mint`], `nft_mint`.
- Token accounts: `vault`, `owner_usdt` [`owner_token`, `owner_ata`], `owner_nft`, `nft_escrow`, `offer_escrow` [`escrow`], `buyer_usdt` [`buyer_token`], `buyer_nft`, `payee_usdt` [`payee_token`], `recipient_usdt` [`recipient_token`].
- Programs: `system_program`, `token_program`, `associated_token_program`, `rent` (fixed addresses in the IDL are used as-is).
- Args are passed **positionally in the order listed in the table above**, so arg names may differ.

### Decisions where guardians-spec.md left a gap (contract author, 2026-11-14)
- **Objections need real, current targets:** a Claim/Hardship objection needs the watched holder's approval bit on it (monitors
  watch approvals; they can't freeze arbitrary items). An objection may be raised any time the target is still open, not only inside the window.
- **One Objection PDA per target, re-usable:** with seeds `["objection", target]`, seats, assets, the estate and the guard could only
  ever get one objection. A resolved objection is therefore overwritten by a new one (the events keep the history); a Dismissed
  objection on a one-off Claim/Hardship can't be re-raised.
- **Upheld Sale** sets the asset back to Held (the "blocked until relisted" rule). **Upheld Hardship** also withdraws the hardship floor.
- **Fallback objections:** every holder is gone and the owner is dead, so **monitors** vote (bitmap `1 << (2·seat + slot)`); 2 decide.
- **Fallback objections lapse (funds are never locked forever; product owner, 2026-11-14):** an Open Fallback objection
  not Upheld by `raised_at + fallback_wait_secs` lapses and counts as Dismissed. After that, votes on it fail (`ObjectionLapsed`).
  Anyone may call `lapse_objection` (Fallback kind only; BadStatus otherwise or if not Open; `ObjectionNotLapsed` if too early)
  to mark it Dismissed, which decrements open_objections and emits ObjectionResolved (upheld = false). `execute_fallback`
  does the same itself when it finds a lapsed objection, so its `objection` account is now **writable**. A lapse does not restart
  the countdown. A dismissed or lapsed Fallback objection can't be re-raised in the same countdown (raised_at ≥ fallback_started_at
  → BadStatus); a restart (upheld objection, or a new recipient after a proven death) allows a new one. Upheld still resets the fallback.
  Instruction `lapse_objection` (no args, anyone): accounts estate, guard(w) `["guard", estate]`, objection(w) `["objection", guard]`.
  New errors: `ObjectionLapsed 6040`, `ObjectionNotLapsed 6041`.
- **Owner signs of life void a started fallback:** `execute_fallback` requires `estate.last_heartbeat < fallback_started_at`
  (heartbeat / veto_death update it), and `start_fallback` may restart a voided countdown. `set_fallback` also resets it.
- **Fallback deaths:** the Guard has no field for a pending report, so `report_fallback_death` only emits an event; the agent's approval
  sets the bit and restarts a running countdown, so family get the full wait to object to the new recipient.
- **Succession:** the wait runs from the confirmation. A backup who reported or confirmed the death is never promoted; a backup
  who has become another seat's holder is skipped (no duplicate verifiers). A monitor who becomes the holder is dropped as monitor.
- **ApprovalStamp** is created (init_if_needed) on every claim's first approval, Guard or not (about 0.0012 SOL rent, paid by `payer`),
  so a Guard added later still finds stamps. Claims approved before this upgrade have no stamp: with a Guard they need one more
  verifier approval (which writes the stamp) before they can execute.
- **Owner-approved claims** (living plans, owner alive) skip the objection window but still stop on an Open objection.
- `start_fallback` / `execute_fallback` need all three Seat accounts, so the owner must create all three seats.
- `execute_fallback` sets the estate status to Unlocked (it may still be Active with an agent-approved death claim).
- Errors beyond the spec list: `BadFallback` (appended last). Events beyond the spec list: `GuardInitialized`, `SeatConfigured`,
  `SeatDeathVetoed`, `ObjectionVoted`, `FallbackDeathReported`, `FallbackDeathReviewed`.

### Disputes (U9)
Reuses the guardians' objection pattern instead of duplicating it: a **dispute is an `Objection` account in the same
`["objection", target]` PDA with `seat_index = DISPUTE_SEAT = 254`** (`monitor` = the disputer). Every check that
already pauses on an open objection (`execute_claim`, `finalize_unlock`; also `accept_offer`, `finalize_succession`)
therefore pauses on an open dispute too, and a target has a monitor's objection or a dispute, never both.
Differences from a monitor's objection: no Guard is needed (works on every estate), it can be raised by an active
beneficiary or a verifier, it is resolved only by 2 of 3 verifiers (`resolve_dispute`; never by `vote_objection`, never by
the owner alone), and it **lapses** at `raised_at + max(estate.waiting_period_secs, 60)`: an Open dispute past that time
counts as Dismissed everywhere (`objection_is_open` and `raise_objection` are lapse-aware), and votes on it fail with
`DisputeLapsed`. Funds can therefore never be locked by a dispute.

## Second security review and independent review (plans 18.2, 18.8 and 18.10)

**This section overrides anything above it that disagrees, and describes the code as it is.** No existing
account layout or PDA seed changed; enum variants, errors and events were only appended. Program and clients
ship together. `RT` (recovery timeout) = 4 x `W`, with `W` = max(waiting period, 60 s). `g` = the waiting period
clamped to 60 s..1 day. `R` = max(fallback wait, 60 s).

### Rules

- **Waiting period and succession wait.** Both read as at least 60 s, also when stored lower (a stored 0 waits
  60 s), so a living owner or holder always has time to answer.
- **Proof of life.** These are signed only by the living owner and set `last_heartbeat`, clear an open death
  claim (status Active again, `DeathVetoed`) and void a countdown started earlier: `heartbeat`, `veto_death`,
  `owner_replace_seat`, `remove_member`, `set_agent`, `set_fallback`, `set_seat_monitors`, the owner's
  `vote_objection` and the owner's `resolve_dispute`. Unlock and Fallback challenges raised before it are void
  with their votes: they block nothing, votes on them fail with ObjectionLapsed, `lapse_objection` closes them
  at once and a new one may be raised. Other owner instructions (deposit, withdraw, owner_approve_claim,
  set_will, rules, assets) are not proof of life.
- **A disproved claim.** An open claim older than `last_heartbeat` (a check-in under the older program, which
  did not clear it) is disproved: `review_death`, `attest_death` and `finalize_unlock` refuse it
  (DeathDisproved), the fallback treats the death as not established, and anyone who may report replaces it at
  once, also in DeathPending (status Active again). Older claims stored with time 0 are always disproved.
- **Who reports the owner's death.** An active beneficiary, a living trusted person or a living listed
  fallback recipient (with `guard`); never the agent (NotParticipant). The agent can't review a claim it
  submitted (OwnApproval). A new claim voids a challenge raised against the one it replaces.
- **Approvals of claims.** `approve_claim` works only when Unlocked; while Active only `owner_approve_claim`
  approves, and that approval still pays after the unlock. Approvals given before the quorum of this death are
  not counted: they count only if the claim was created after `death_pending_since`, or the stamp's
  `approved_at >= death_pending_since`, or the stamp is collecting (`approved_at == 0`, `seat_index == 255`).
  `death_pending_since` is when the quorum was reached, so approvals given during the death's wait (under an
  older program) count. Others neither pay nor block: the next approval resets the bitmap.
- **Quorum** (death, claim, hardship) = min(needed, eligible), never zero. `needed` is the threshold
  (max(threshold, 2) when Referred). `eligible` is the held seats other than whoever gains (the claimant, the
  hardship's beneficiary, the death claim's submitter). Only their bits count; a successor holds the seat's vote.
  Signing again is accepted only when it completes a quorum that is not met; otherwise AlreadyApproved.
- **A lost quorum (claims).** Each approval drops the votes of seats that no longer decide. A claim's approvals
  stand only if no counted vote has been lost to a vacancy, unless what remains still reaches the full threshold.
  So a quorum that drops below the threshold through a vacancy needs another approval, which stamps a fresh
  objection window; one that only becomes smaller (fewer eligible seats, no vote lost) still pays.
- **The only trusted person left, who gains.** When no other seat is held and the agent Approved (never
  Referred), that person may attest the death or approve their own claim. It is marked by bit 7 of
  `death_attestations` / `approvals` (DECIDED_ALONE): the unlock then waits twice the waiting period and the
  claim twice the objection window. Not for hardship.
- **Replaceable reports.**

  | Report | Another person may replace at | Whoever made it, at |
  |---|---|---|
  | Death claim, unreviewed | never (the agent's rejection frees it; a lost agent is replaced, below) | never |
  | Death claim, reviewed, no quorum | reported + 2W | reported + 2W + g |
  | Seat death, unreviewed | reported + g | reported + 2g |
  | Seat death, reviewed, not confirmed | reported + RT + 2W | reported + RT + 2W + g |
  | Fallback death, unreviewed | reported + min(g, R/2) | twice that |
  | Fallback death, reviewed | reported + 2R | reported + 2R + min(g, R/2) |

  A confirmed report is never replaceable. With no living seat a reviewed death claim is not replaceable: it is
  the fallback plan's proof. A disproved claim is replaced at once. Because an unreviewed death claim stays, its
  `death_pending_since` is when this death's first open claim was made. A new seat report voids a challenge to
  the one it replaces.
- **Confirming a seat's death.** Never the reporter, the holder, the agent, or `backups[0]` unless they hold
  another seat (they can't be promoted then). Who may:
  - the holder of another seat;
  - `backups[1]` or a monitor of the seat, when no other seat is held or the approved report has waited RT;
  - an active beneficiary, when no other seat is held and nobody watches the seat (a monitor other than
    `backups[0]`, or `backups[1]`), or when the approved report has waited RT.
- **Confirmations the owner revokes.** When the owner replaces a holder, changes a seat's monitors or removes a
  beneficiary, a seat report confirmed by someone who then holds no seat is cleared at once, the whole report and
  not only the confirmation (SeatDeathReportCleared); the owner's replacement also clears the replaced seat's own
  report. A check-in
  revokes nothing, and a confirmer who has since died keeps the confirmation.
- **Finalizing a succession.** A report or confirmation by whoever is now the agent is cleared. The first
  backup who is not the owner, the agent, a holder of another seat, the reporter or the confirmer takes the seat;
  the other backup stays a backup (also one who reported). When only the reporter or confirmer could take it: if
  nobody watches the seat and no other is held, that backup takes it RT after the confirmation (before that,
  WaitingPeriodNotOver); otherwise the report is cleared for a fresh one. The seat vacates when every backup is
  the owner, the current agent or the holder of another seat (or there is none).
- **Fallback.** The death is established when Unlocked, or when the claim is Approved or Referred and not
  disproved. A countdown is valid only if `last_heartbeat < fallback_started_at` and
  `death_pending_since <= fallback_started_at`. It pays at the later of `started + max(fallback wait, 60 s)`
  (twice that while Active with a Referred claim) and the death's own wait (`death_pending_since` plus the
  waiting period while Active, plus the unlock delay while DeathPending). An open Unlock challenge blocks it, as
  does an open Fallback objection; a Fallback objection lapses after R, and one raised before the owner's last
  sign of life or before the current countdown started is void. Recipients can't be the estate (BadFallback);
  one that an older list names is skipped. The payment goes to the recipient's ATA (created if missing) or any
  other token account of the mint they own.
- **After the fallback ran** no rule reserves anything in `sweep_residual`.
- **Disputes.** The living owner (Active or DeathPending) decides a dispute alone. Trusted people decide claim
  disputes only after the unlock (NotOwner before). Once resolved, `raised_at` is when it was resolved, and a
  claim's objection window runs from there.
- **Challenges.** Monitors may take over an unlock's open dispute. Once a monitors' objection is resolved,
  `raised_at` is when it was resolved. With a Guard an offer waits out the objection window before it is
  accepted, and so does a hardship's quorum (its `["stamp", hardship]`); an offer made at or before an upheld
  sale objection was decided can't be accepted (OfferTooOld).
- **Nobody in their own favour.** Whoever gains can't approve outside the route above (OwnApproval), raise the
  one challenge (OwnClaimDispute) or vote to dismiss one (OwnApproval); they may vote to uphold. Votes of vacant
  seats don't count. Fallback votes: one wallet, one vote.
- **Agent replacement.** By the owner while Active (`set_agent`), or by trusted people (`vote_agent`): every
  held seat (at least two) before the unlock, two or the only one left after it. Also two (or the only one) before
  the unlock when a death claim is open, not disproved and still unreviewed, has stood for RT since it was made
  (an unreviewed claim can't be replaced, so this is this death's first claim), and the owner has shown no life
  for RT. **A lone voter who gains (N2).** When the voter's own vote would be the whole quorum (the only seat
  held) and they gain (the open death claim is theirs, or they are an active beneficiary), it replaces the agent
  only after 2 x RT: before the unlock, measured from the later of the owner's last sign of life and the claim
  (still unreviewed); after it, from when their own open claim was made, while the agent has not approved it (no
  such claim: never alone). Otherwise WaitingPeriodNotOver. No new storage: the voter's Beneficiary PDA is the first
  remaining account (missing or wrong: counted as one who gains), the claim the second. A new agent sets back what
  the old one reviewed: the death claim's verdict (with its attestations; the
  status is Active again and the claim's time restarts), seat reports (verdict Pending, confirmation cleared) and
  fallback reports (verdict Pending), emitting AgentReviewCleared. A candidate can't be a backup (BadAgent).
- **What the agent may not be or do.** It can't be a trusted person (create_estate, owner_replace_seat) or a
  backup (set_seat_backups, set_agent, vote_agent), is never promoted, can't report the owner's, a seat's or a
  fallback recipient's death, confirm one, review a claim, hardship or report that it made or that is its own,
  be the buyer, or accept an offer without a co-signer. It may be a beneficiary, payee, monitor or fallback
  recipient; as a monitor it can raise and vote on objections.

### Mixed versions

Every instruction whose arguments or account list changed fails on the new program when an old client sends it
(missing data or accounts), and `add_rule_v2` fails on the old program. The reverse is not true: the deployed
program ignores trailing arguments and accounts, so a new client talking to the old program is silently
misread on these: `accept_offer` (no amount or co-signature check), `review_fallback_death` (the old program marks
the recipient dead at once), `review_death`, `review_seat_death`, `approve_hardship`, `confirm_seat_death`,
`execute_claim`, `execute_scheduled`, `execute_fallback`, `owner_replace_seat`, `raise_dispute`,
`report_fallback_death`, `report_seat_death`, `set_agent`, `set_fallback`, `submit_death_claim`,
`sweep_residual`, `vote_agent`. Instructions whose layout didn't change but whose rules did (`heartbeat`,
`vote_objection`'s owner, and others above) behave as the deployed program there. So the client must refuse to
write unless the deployed program is the one its IDL was built from.

### Limits kept (documented, not fixed)

- Agent votes are bound to the agent they replace, not to a round: if the agent changes and returns, votes cast
  against it earlier count again (L4). A round would need a field in AgentVote or Estate.
- A referred claim with one trusted person left is paid by that person (the quorum is min(needed, eligible)):
  "a referred claim needs two" holds only while two may decide (L14).
- `sweep_residual` pays the fallback list without the fallback countdown once the estate is Unlocked.
- Votes on Succession objections and claim disputes cast before the owner replaced the voter still count until
  the challenge lapses or the owner decides it.
- A living trusted person who doesn't answer an approved report of their death for RT, nor veto it during the
  succession wait, is replaced on a beneficiary's confirmation (N3). That is the price of H3, which keeps an estate
  recoverable when every trusted person has died.
- The only trusted person left, who is also the one who gains, can still replace the agent alone and then decide
  alone, but only after 2 x RT with the death claim unreviewed and no sign of life, or with their own claim
  unapproved for 2 x RT after the unlock (N2). Refusing it outright would lock an estate whose only trusted person
  is the only heir and whose agent is lost. A lone heir whose only request is a hardship has no clock (a Hardship
  stores no time), so files a claim to start one.

### Client notes

- A report cleared by `finalize_succession` can be followed by a fresh report in the same transaction.
- Removing a payee or beneficiary doesn't end their rules; send `end_rule` with the removal when it should.
- A title mint must give up both authorities before `register_asset`.
- `finalize_succession` reads no remaining account any more.
